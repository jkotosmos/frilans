# Деплой

Текущий, действующий путь — **GitHub Pages из статического экспорта**, без
базы данных и без сервера. Второй раздел ниже — как заново поднять полную
динамическую версию (реальная регистрация, PostgreSQL, Server Actions),
которая уже была реализована и осталась в git-истории.

## GitHub Pages (текущий путь)

Сайт собирается через `next build` с `output: "export"` (см.
`next.config.mjs`) в каталог `out/`, а `.github/workflows/deploy-pages.yml`
на каждый push в `main` пересобирает его и публикует в ветку `gh-pages`.

### Разовая настройка

1. Смержите/запушьте этот код в ветку `main` репозитория (или, если ветку
   `main` заводить пока не хотите, запустите workflow вручную — см. ниже).
2. В репозитории: **Settings → Pages → Build and deployment → Source** —
   выберите **Deploy from a branch**, а не "GitHub Actions" (это два разных
   режима; нужен именно первый).
3. Там же **Branch** — выберите `gh-pages` / `/ (root)`. Ветки `gh-pages`
   ещё не существует до первого запуска workflow — GitHub позволит выбрать
   её сразу после первого успешного запуска (см. следующий шаг), не раньше.
4. Запустите публикацию:
   - автоматически — push в `main` запускает `deploy-pages.yml` сам;
   - или вручную прямо сейчас, не дожидаясь `main`: вкладка **Actions** →
     **Deploy to GitHub Pages** → **Run workflow** → выберите нужную ветку.
5. После первого успешного запуска в репозитории появится ветка `gh-pages`
   с собранным `out/` — вернитесь к шагу 3 и выберите её, если ещё не
   выбрали. Сайт будет доступен на `https://<владелец>.github.io/<репозиторий>/`
   (для этого репозитория — `https://jkotosmos.github.io/frilans/`).

Дальше каждый push в `main` пересобирает и переразворачивает сайт
автоматически — ничего больше делать не нужно.

### basePath: если название репозитория изменится

`next.config.mjs` жёстко задаёт `basePath`/`assetPrefix` как `/frilans` —
GitHub Pages отдаёт **project pages** (в отличие от `<user>.github.io`) по
адресу `https://<user>.github.io/<repo>/`, и без `basePath`, совпадающего с
именем репозитория, все ссылки на статику (`_next/...`) будут указывать не
туда. Если репозиторий переименуют или сайт переедет на кастомный домен —
поменяйте `REPO_BASE_PATH` в `next.config.mjs` (на новое имя репозитория,
либо на `""` для кастомного домена/`<user>.github.io`-репозитория) и
пересоберите.

### Что важно понимать про этот режим

- Данные — снимок `src/data/seed-data.json`, не живая база. Обновляются
  только пересборкой (см. `scripts/export-static-data.ts`, требует реальный
  Postgres — актуально только если восстанавливаете динамическую версию).
- Личный кабинет открыт всегда, без входа — это осознанное решение (см.
  README «Текущий режим»), не баг доступа.
- Формы входа/регистрации/заказа/сообщений видны и кликабельны, но не
  отправляют данные — вместо этого показывается тост «демо-версия».
- CI (`.github/workflows/ci.yml`) — typecheck, lint и `next build` на каждый
  push/PR, независимо от публикации.

## Полная динамическая версия

Настоящая регистрация, PostgreSQL, NextAuth-сессии, Server Actions — всё это
было полностью реализовано и работало до перехода на статический демо-режим.
Код никуда не делся, он в git-истории этой ветки: `lib/actions/*`, `lib/auth.ts`,
`lib/db.ts`, `lib/rate-limit.ts`, `lib/telegram-auth.ts`,
`prisma/schema.prisma` (`provider = "postgresql"`), `src/middleware.ts`,
`src/app/api/auth/[...nextauth]/route.ts`.

Чтобы вернуться к ней:

1. Найдите коммит до перехода на статический экспорт (последний, где ещё
   существуют перечисленные выше файлы — `git log --diff-filter=D --
   src/lib/db.ts` покажет коммит, который их удалил; интересующее вас
   состояние — на один коммit раньше).
2. Верните `next.config.mjs` к обычному режиму (уберите `output: "export"`,
   `basePath`, `assetPrefix`) и восстановите удалённые файлы из этого коммита.
3. Дальше — как раньше:
   - заведите PostgreSQL (бесплатно — [Neon](https://neon.tech),
     [Supabase](https://supabase.com), либо `docker run -d -p 5432:5432
     -e POSTGRES_PASSWORD=postgres postgres` локально);
   - `DATABASE_URL="postgresql://..." npx prisma db push`;
   - опционально — `DATABASE_URL="postgresql://..." npm run db:seed` для
     демо-данных (создаёт аккаунты с известным паролем `Password123!` — не
     делайте этого в настоящем проде);
   - задеплойте на [Vercel](https://vercel.com) (сам определяет Next.js,
     переменные окружения — `DATABASE_URL`, `NEXTAUTH_SECRET`
     (`openssl rand -base64 32`), `NEXTAUTH_URL`) либо через Docker
     (`Dockerfile` + `.github/workflows/docker-publish.yml`, публикует в
     `ghcr.io/<owner>/<repo>` — сейчас запускается только вручную, `workflow_dispatch`,
     см. комментарий в файле).
4. Прочитайте [`SECURITY.md`](./SECURITY.md) целиком — он описывает именно
   эту версию (аутентификацию, rate limiting, CSRF/XSS-защиту, security
   headers) и что доделать перед настоящим продакшеном.

**Честная оговорка:** `Dockerfile` собран по стандартному, хорошо известному
паттерну для Next.js + Prisma (multi-stage build, тот же базовый образ на
этапе сборки и рантайма — во избежание проблем с glibc/musl у нативного
Prisma-движка), но собрать образ в песочнице, где писался этот код, не
получилось: Docker Hub был заблокирован политикой исходящего трафика той
сессии (подтверждённый policy denial, не ошибка конфигурации). Реальная
сборка в GitHub Actions такому ограничению подвергаться не должна, но при
первом запуске `docker-publish.yml` стоит проверить его лог.
