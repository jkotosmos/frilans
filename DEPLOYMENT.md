# Деплой

Два пути, оба стартуют с GitHub. **Vercel — рекомендуемый** для этого проекта:
Next.js — их собственный фреймворк, деплой из GitHub-репозитория настраивается
за пять минут и не требует Dockerfile вообще. Второй путь — self-hosted через
Docker, если нужен свой сервер/провайдер.

Independent от выбора пути: **сначала прочитайте раздел «База данных» ниже** —
это единственный обязательный шаг перед любым из двух путей.

## База данных: SQLite → PostgreSQL

Локально проект использует SQLite (`prisma/dev.db`) — это файл на диске, что
отлично для разработки, но не работает в проде: у serverless-функций (Vercel)
файловая система эфемерна и часто доступна только на чтение, а на классическом
сервере файл на диске означает отсутствие резервного копирования, репликации и
конкурентного доступа из нескольких инстансов. Перед любым реальным запуском:

1. Заведите бесплатную PostgreSQL-базу — подойдёт
   [Neon](https://neon.tech), [Vercel Postgres](https://vercel.com/storage/postgres)
   или [Supabase](https://supabase.com). Получите connection string вида
   `postgresql://user:password@host/dbname?sslmode=require`.
2. В `prisma/schema.prisma` смените:
   ```diff
   datasource db {
   -  provider = "sqlite"
   +  provider = "postgresql"
      url      = env("DATABASE_URL")
   }
   ```
3. Примените схему к новой базе (один раз, с реальным `DATABASE_URL`):
   ```bash
   DATABASE_URL="postgresql://..." npx prisma db push
   ```
4. Если это демо-запуск, а не боевой проект — можно засеять базу тестовыми
   аккаунтами тем же способом: `DATABASE_URL="postgresql://..." npm run db:seed`.
   **Не делайте этого для настоящего продакшена** — сид создаёт аккаунты с
   известным всем паролем (`Password123!`).

Остальная часть схемы (модели, индексы) не завязана на SQLite и переносится
как есть — единственное, что менялось при первоначальной разработке именно
из-за SQLite, это enum-поля, хранящиеся как `String` (см. комментарий в
`schema.prisma`); при желании на Postgres их можно позже перевести на нативные
Prisma `enum`, но это не обязательно для запуска.

## Путь A: Vercel + GitHub (рекомендуется)

1. На [vercel.com](https://vercel.com) → **Add New Project** → выберите этот
   GitHub-репозиторий (`jkotosmos/frilans`), ветку для продакшена — обычно `main`.
   Vercel сам определит, что это Next.js — дополнительная настройка сборки не нужна.
2. В **Environment Variables** укажите:

   | Переменная | Значение |
   |---|---|
   | `DATABASE_URL` | connection string из шага выше |
   | `NEXTAUTH_SECRET` | `openssl rand -base64 32` — свежий, не из `.env.example` |
   | `NEXTAUTH_URL` | ваш прод-домен, например `https://artel.example.com` |
   | `TELEGRAM_BOT_TOKEN` | опционально, см. `TELEGRAM.md` |

3. **Deploy**. Дальше каждый push в продакшн-ветку деплоится автоматически, а
   каждый Pull Request получает свой preview-деплой с отдельным URL — это
   бесплатно и включено по умолчанию, ничего дополнительно настраивать не надо.
4. После первого деплоя откройте сайт, попробуйте регистрацию и вход — это
   быстрее всего покажет, если `DATABASE_URL`/`NEXTAUTH_SECRET` не подхватились.

**Важная оговорка про rate limiting.** `lib/rate-limit.ts` — лимитер в памяти
процесса (см. `SECURITY.md`). На Vercel каждый serverless-вызов может попасть
в новый инстанс, так что это ограничение работает менее строго, чем на одном
постоянно работающем сервере. Для реального продакшена под нагрузкой замените
на общий стор (Upstash Redis — у него как раз есть нативная интеграция с Vercel).

## Путь B: Docker / self-hosted

Файлы уже готовы: `Dockerfile` (многоэтапная сборка, `output: "standalone"` в
`next.config.mjs`) и `.github/workflows/docker-publish.yml`, который на каждый
push в `main` собирает образ и публикует его в GitHub Container Registry
(`ghcr.io/<owner>/<repo>`) — не нужно заводить отдельный registry или секреты,
используется встроенный `GITHUB_TOKEN`.

Что нужно сделать самостоятельно после этого — «раскатать» готовый образ на
свой сервер (Fly.io, Railway, Render, обычный VPS с Docker). Общий вид:

```bash
docker pull ghcr.io/<owner>/<repo>:latest
docker run -d -p 3000:3000 \
  -e DATABASE_URL="postgresql://..." \
  -e NEXTAUTH_SECRET="..." \
  -e NEXTAUTH_URL="https://ваш-домен" \
  ghcr.io/<owner>/<repo>:latest
```

Точный способ автозапуска зависит от хостинга (systemd-юнит, docker-compose,
панель управления провайдера) — сюда сознательно не включён единственный
«правильный» вариант, поскольку он у каждого свой.

**Честная оговорка:** `Dockerfile` собран по стандартному, хорошо известному
паттерну для Next.js + Prisma (multi-stage build, тот же базовый образ на
этапе сборки и рантайма — во избежание проблем с glibc/musl у нативного
Prisma-движка), но я не смог собрать образ в этой песочнице: Docker Hub
заблокирован политикой исходящего трафика этой сессии (не ошибка конфигурации
— это подтверждённый policy denial). Реальная сборка в GitHub Actions такому
ограничению подвергаться не должна, но при первом запуске `docker-publish.yml`
стоит проверить его лог сборки.

## Чек-лист после первого деплоя (любой путь)

- [ ] База данных — PostgreSQL, не SQLite (см. выше)
- [ ] `NEXTAUTH_SECRET` — свежий случайный, не значение из `.env.example`
- [ ] `NEXTAUTH_URL` — реальный HTTPS-домен (нужно и для secure-cookies, и для Telegram)
- [ ] Регистрация и вход проверены вручную на самом деплое
- [ ] Прочитан раздел «Before a real production launch» в `SECURITY.md` —
      там про платежи, независимый security-аудит и то, что там ещё смоделировано
